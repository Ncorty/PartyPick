# Запуск PartyPick на VPS

Это подготовка одноузлового запуска. Публичный сервер и домен пока не выделены;
проверка между устройствами и публичная ссылка остаются отдельной задачей.

## Перед запуском

- VPS с Linux, Docker Engine и современной Docker Compose (`docker compose`).
  Для небольшого лобби достаточно начать с 2 ГБ RAM и контролировать нагрузку.
- Домен с A-записью на IPv4 VPS. Добавляйте AAAA только при настроенном и
  проверенном входящем IPv6: стандартная конфигурация публикует IPv4.
  Откройте входящие TCP 80 и 443;
  PostgreSQL и API наружу не публикуются.
- Учётная запись оператора с доступом к Docker. Доступ к Docker равен
  административному доступу к контейнерам и их секретам.
- Убедитесь, что внутренняя подсеть `172.30.77.0/29` не конфликтует с сетью VPS.
  Если меняете её, одновременно измените адрес Caddy и `TRUSTED_PROXY` в Compose.

Скопируйте `.env.example` в `.env` и укажите домен в `SITE_ADDRESS`, полный
HTTPS origin без завершающего `/` в `PUBLIC_ORIGIN`. Сгенерируйте два независимых
пароля, например `openssl rand -hex 32` для каждого. Не помещайте `.env` в Git.
Перед записью секретов установите `umask 077`, а права готового `.env` проверьте
командой `chmod 600 .env`.
Если пароль содержит `$`, `#`, пробелы или символы URI, задайте его в `.env`
в одинарных кавычках: `APP_DB_PASSWORD='пример$сложного#пароля'`.
API получает поля подключения отдельно и не собирает URL с паролем.

Роли и пароли PostgreSQL создаются только при первом запуске с пустым томом.
Последующее изменение `.env` не меняет пароль существующей роли: ротация требует
согласованного изменения пароля в БД и настройки API с последующим перезапуском.
Не удаляйте рабочий том для смены пароля.

```sh
docker compose up --build -d --wait
docker compose ps
curl --fail https://ВАШ-ДОМЕН/api/health
```

Caddy получает публичный сертификат автоматически и сохраняет его в томе.
Не удаляйте тома при обычном обновлении. `GET /api/health` проверяет запрос к БД;
при недоступной БД API перестаёт быть готовым. `docker compose logs --tail=100`
показывает состояние служб. Доступы по URL не логируются; в журналах Caddy
поля запроса и ошибки с путями скрыты, а API не печатает URL запросов.

## Резервная копия и проверка восстановления

```sh
sh deploy/backup.sh
sh deploy/restore-check.sh backups/partypick-ИМЯ.dump
```

Копия создаётся через `pg_dump -Fc` в локальном каталоге `backups/` с приватными
правами. Команда проверки создаёт **новую временную БД**, восстанавливает дамп
через `pg_restore --no-owner --no-acl --exit-on-error`, проверяет таблицы и
удаляет временную БД. Рабочая `partypick` не перезаписывается.
Для остановленной записи можно дополнительно сравнить содержимое всех четырёх
таблиц с текущей БД: `EXPECT_SAME_AS_LIVE=1 sh deploy/restore-check.sh ...`.
При продолжающихся изменениях сравнение с живой БД может дать ложное расхождение,
поскольку дамп использует собственный согласованный снимок.

Храните копии вне VPS, шифруйте их и регулярно проверяйте восстановление.
Локальный том PostgreSQL и файл в `backups/` на том же сервере не защищают
от потери VPS. Установите периодическое выполнение копирования и политику
хранения до приёма пользовательских данных.

## Обновление и откат

Перед обновлением создайте копию и проверьте её восстановление. Сохраните
идентификатор текущего Git-коммита и образов (`docker compose images`). Затем:

```sh
git pull --ff-only
docker compose up --build -d --wait
curl --fail https://ВАШ-ДОМЕН/api/health
```

При ошибке вернитесь к предыдущему проверенному коммиту и повторите
`docker compose up --build -d --wait`, не удаляя томов. Схема пока создаётся
идемпотентно без откатных миграций; перед будущими изменениями схемы нужен
отдельный план восстановления из копии. `docker compose down` сохраняет тома,
а `down --volumes` удаляет данные и сертификаты и не применяется при обычном
откате.

## Границы

Конфигурация рассчитана на один API и один PostgreSQL на одном VPS.
Ограничение частоты запросов хранится в памяти API. Несколько экземпляров
потребуют общего хранилища лимитов и отдельного решения для БД. Публичная
проверка и совместный проход с разных устройств возможны после появления
VPS и домена; локальные тесты используют изолированный сертификат.

Конфигурация проверена в [контейнерном CI](https://github.com/Ncorty/PartyPick/actions/runs/43757901676):
сборка образов, обе конфигурации Caddy, HTTPS, совместная комната, конкурентное
изменение версии, сохранность после перезапуска и восстановление дампа с полным
сравнением четырёх таблиц. Публичный сертификат и сеть будущего VPS этим прогоном
не проверяются.
